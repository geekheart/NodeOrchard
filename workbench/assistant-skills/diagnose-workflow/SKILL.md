# 先取应用已有证据

1. 先使用当前上下文与服务端已校验的诊断证据，明确所选旧运行、最新运行与当前草稿各自的身份和版本。缺少运行详情再读取 `workflow.run`；查看最新运行时使用其实际节点身份。没有工作流时用 `workflows.list` 定位，多个候选影响结论时再确认对象。
2. 按证据缺口读取失败节点的错误、时序、尝试版本、stdout/stderr 与 partialText；partialText 只是可见过程。需要工具执行依据时用关联 sessionId 读取 `session.history`；已有产物用 `artifact.inspect` 按运行、节点和登记 ID 检查。独立只读检查可按协议合并请求，已取得的结果不重复查询；省略、过期或不可读的内容如实标注。
3. 涉及节点能力时使用已提供的能力说明；缺少契约再读取 `node.describe` 或 `app.capabilities` 对应分区。注册工具与代码模式是两种实现路径，目录缺项不等于不能写业务代码。Python 依赖用 `runtime.inspect` 核对实际解释器及所需模块。
4. 界面异常按需用 `browser.capture` 截图或短录制，标注隔离页面差异。证据足以支持业务配置修改时用 `workflow.propose`，软件源码问题交付定位依据。调用超时或失败后保留已查事实和失败阶段，不将同一方案自动再请求一遍，不把检查点当作应用或运行授权。

完成标准：结论对应具体运行、节点、版本和证据，区分事实与推测，并说明下一步可以验证什么。读取失败应报告工具给出的原因；不让用户补贴仍可通过现有工具读取的日志。提出方案不代表已经修复或重跑。

待处理状态：旧助手失败被明确重试接续、或用户手动结束关注，仅表示聊天事项已收敛；业务运行和人工审核继续按真实版本判断。不能把回复完成、提案应用或待处理数量减少说成业务已修复，也不能替用户结束审核。
