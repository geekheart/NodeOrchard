# 修改用户指定的业务步骤

1. 先使用本轮已提供的编辑协议、节点契约和运行环境事实；仅缺少的部分再用 `app.capabilities`、`node.describe` 或内部代码Skill补齐。自由对话先由AI分类；创建／修改进入专用候选生成，不先重复发现整套诊断工具。
2. 从当前草稿确定最小修改范围，保留未涉及节点、连线、固定 Skill 版本与用户已有配置。审核修改先核对绑定的运行、尝试、全部产物哈希和生产目标：Skill 目标消费反馈走对应审核卡；所有工具产物反馈都通过“生成修改候选”单击提交完整意见与版本绑定的 `revisionRequest`，先完成 AI 分类，无需用户再次发送。绑定与权限校验通过后，`workflow` 和 `feedback` 都进入核心业务代码候选生成，保留真实分类；普通反馈仍走原有流程。其它意图遵循审核文档中的边界。工具下游连接 Skill 也走代码候选路径。用户要求替换产出能力时，修改真正的产出步骤；增加一个前置配置节点不能算完成替换。
3. 通过 `workflow.propose` 生成可审阅候选。当前 `update-node` 不能改类型；Skill 换成 Python 能力可在原坐标新增 `tool` 的代码模式节点，移除冲突旧连线、连接对应上下游，再移除旧 Skill。新节点使用新引用，按实际端口类型连接；检查人工审核目标和 Skill 改进范围中的旧引用。工具节点不能充当可学习的 Skill。此路径保留业务位置与职责，不承诺保留原 nodeId。
4. 在同一对话展示修改明细，供用户明确应用，再通过运行入口明确新建运行。已有运行保留冻结代码、审核与产物；候选生成和应用草稿不续跑旧运行，也不增加其审核修改计数。人工要求修改不限次数，历史计数仅供追溯；自动重试、候选自动修复、模型调用预算和循环执行仍遵守各自限制。`workflow.preflight` 是配置和输入准备检查，不等于新代码已成功执行。详细边界见 `docs/workflow-conversation.md` 的“审核、重做与反馈”。

完成标准：候选通过现有编辑校验；工具产物反馈已落实为真实业务代码变化，标题、注释或占位配置变化不算完成；用户要求的实际节点替换已包含在候选中，相关连线与引用一致，其余流程保留。分别报告“候选已生成”“已应用”“已执行验证”的真实进度。

范围：独立会话只修改服务端绑定的当前工作流；总控按当前权限和明确目标使用目录中的跨工作流接口。业务代码候选还需自定义节点权限。权限设置仅供用户在设置页修改，助手不以提案改变权限或工作目录授权。应用开发或测试任务不授权修改用户真实工作流；验证使用隔离 fixture。没有专用执行工具时，由用户通过现有运行入口执行，不能借维护工作自动运行、重试或修改业务记录。

节点派生：获准后用 `workbench.inspect` 的 `section: node-derivations` 读取直接父级与固定版本；父级未记录保持未知。登记及发布由界面核对来源，编辑候选保留 `origin`。详见 `docs/workflow-node-system.md`。

图片及软件工具：先用 `workbench.inspect(section="integrations")` 核对真实就绪状态，再按 `node.describe("skill")` 准备已安装 Skill 的固定版本及 `requiredToolsets`。模型产图使用 `image_gen`，连接 human 审核再交付；MCP、浏览器和 Computer Use 只请求已配置的真实工具集。缺少 Skill 时说明人工新建入口，不以文字或文件名冒充新能力，不改提供商、连接、认证或权限。缺失状态、候选及真实执行分别报告，见 `docs/skill-integrations.md`。

学习配置：`improvement.scope` 支持 `skills`、`tools`、`workflow`，分别限定 Skill 正文、指定工具核心配置或内部业务图；目标字段及冻结边界见 `docs/learning-protocol.md`。通过编辑候选准备支路，由用户在学习面板明确启动；保留评价、审核及来源，不能以诊断读取训练答案或自动应用最佳版本。
